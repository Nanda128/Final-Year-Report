\section{Primary Deliverable}\label{sec:primary-deliverable}

\subsection{BEACON System Overview}\label{subsec:beacon-system-overview}

BEACON's five-page flow from Landing, to Setup, Simulation, NASA-TLX, and Debrief, reflects the typical lifecycle of a maritime search and rescue (MSAR) operation.

The Landing page provides an introduction to the system, and introduces scenario presets, including a tutorial.
The user can then choose to proceed to the Setup page, or to a dedicated Management page.

The Setup page allows users to choose the number of drones, the mission boundary, and the scenario seed.
Here, they can also list the amount of anomalies on the map, such as people in the water, lifeboats, or debris.
They can also tweak sensor settings here.
This page is intended to act as the planning stage and supports experimentation with different mission parameters.

    \caption{A screenshot of a section of BEACON's setup page.}
    \label{fig:beacon_setup_page}
\end{figure}

After setup, the user can then navigate to the Simulation page, which is the core of the system.
This page runs the real-time simulation of the drone swarm across the map, presenting the canvas, alerts, metrics, and mission controls.
The user can pull up a control panel from the bottom of their screen to access controls like drone commands, search pattern generation, and more.
Here, they can also enable administrative tools like enabling or disabling Fog-of-War, which hides anomalies until they have been detected by a drone, or enabling comms degradation simulation.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\linewidth]{beacon_simulation_page}
    \caption{A screenshot of a section of BEACON's simulation page.}
    \label{fig:beacon_simulation_page}
\end{figure}

The user can then end the mission to navigate to a page that prompts the user to fill in an optional NASA-TLX questionnaire, to capture their perceived workload during the mission.
Choosing to fill in the questionnaire then leads to the dedicated NASA-TLX page, after which the user is navigated to a debrief page which presents the user with their weighted NASA-TLX score and a summary of performance metrics.
The user can export this data as JSON, or CSV, to allow for further analysis.

In addition to the above, there is a dedicated Management page, which allows users to manage their scenarios, and view past performance data.
Missions completed on the same session and browser are stored in the browser's local storage, and can be viewed here.
Alternatively, users can also import and export their performance data as JSON files.

These JSONs would then be analysed to determine insights about the system's performance, and possible improvements for the MSAR operations team.

\subsection{Environment and Scenario Modelling}\label{subsec:environment-and-scenario-modelling}

The environment generator creates a bounded rectangular mission space with a configurable width and height.
The generator then populates the environment with a configurable number of anomalies, which can be people in the water, lifeboats, or debris, or false positives.
Each anomaly has its own detection radius, which is the furthest distance in meters at which a drone under ideal conditions could detect it.
Here, environmental effects like the sea state that affect drone speed, sensor performance, and communication range are also modelled.

Pre-defined scenario presets are also included, intended to reflect plausible MSAR scenarios, to allow for easier system testing and evaluation.
These presets include a ``Calm Bay'', ``Rough Sea'', ``Comms Degradation'', and ``High-Stress'' scaling test scenario, each with different parameters to test different aspects of the system.

\subsection{Swarm Behaviour, Coverage Planning, and Communication Degradation modelling}\label{subsec:swarm-behaviour-coverage-planning-and-communication-degradation-modelling}

Swarm behaviour is defined via a weighted Voronoi Tessellation approach, defining cells on the map that are assigned to drones based on their current position and speed in such a manner to optimise search coverage and ensure that drones complete their tasks at roughly the same time.
This is intended to avoid situations where some drones have open capacity while others are overwhelmed, leading to suboptimal search coverage and increased operator workload.

The search area is partitioned into a variety of polygonal ``cells'', each having an area directly proportional to the drone's speed.
This gives each drone an implicit ``territory'' to search.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\linewidth]{voronoi_cells}
    \caption{A screenshot of BEACON's simulation page, showing the division of the map into 5 Voronoi cells, with the cell for Drone 1 highlighted in blue.}
    \label{fig:voronoi_cells}
\end{figure}

For each cell, a set of waypoints is generated using a Boustrophedon (Lawnmower) path planning algorithm (\cite{10.1007/978-1-4471-1273-0_32}), to ensure systematic coverage.
This approach provides a predictable and explainable search pattern, despite being less adaptable than more complex reinforcement learning-based approaches like EN-MASCA (\cite{ENMASCA2025})\@.
These paths are then rendered via canvas layers, and the drones are given a set of waypoints to follow sequentially, before returning to the Drone Hub in the centre of the map.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\linewidth]{voronoi_cells}
    \caption{A screenshot of BEACON's simulation canvas, showing the map, divided into 5 Voronoi cells, with Boustrophedon paths drawn on the map. Highlighted is the path for DR-01, with each Blue Dot representing a waypoint for the drone.}
    \label{fig:lawnmower_path}
\end{figure}

The communications model seeks to simulate the effects of communication degradation on the drone swarm, by introducing configurable communication ranges, and a probabilistic model of communication failure based on distance and environmental effects.
Packet loss can occur based on the drone's distance from the Drone Hub, as well as the predefined sea state, and other factors defined in the scenario configuration.
By default, the system uses information based off of~\cite{s21082848}, assuming the drones are operating in a fourth-generation long-term evolution (4G LTE) network.

The delay can get larger and larger as the conditions get worse, until a point where the drone is effectively disconnected from the Drone Hub, and must rely on its last known instructions and local decision-making to continue its mission.
Any detections made while disconnected get stored in the drone's local memory as a ``buffer'' of queued messages, which are then sent to the Drone Hub all at once when the drone reconnects.
Packet drops and delays drive alert generation to influence situational awareness and impact workload, similar to real-world MSAR operations where communication issues are common and have significant impacts on mission success.

Together, these models create realistic and controllable perturbations that allow the accurate replication of real-world MSAR challenges.

\subsection{User Interface and Interaction Design}\label{subsec:user-interface-and-interaction-design}

BEACON's simulation interface utilises a single, stable frame with a modular ``children'' module for route-specific content.
This allows an extensible interface architecture, and simple comparisons between different interface designs, while keeping the same underlying scenarios and mechanics.

Within the simulation page, information is separated into a metrics dashboard, a central Map, an Alerts panel, an environmental details box, and a pull-up control panel.
This separation follows the Proximity Compatibility Principle (\cite{doi:10.1518/001872095779049408}), grouping related information and actions together so operators can parse mission state quickly under time pressure.

To manage cognitive overload from alerts, the Alerts panel includes a searchable alert log.
Each alert is categorised with aviation crew alerting conventions (\cite{RN3}), with the option to acknowledge alerts individually or in bulk, which mutes the alert but keeps it visible in the log.
Each alert is also accompanied by an audio cue, with different sounds for different alert levels.
These mechanics were added to support triage and alert prioritisation without hiding historical context, helping preserve situational awareness when alert volume increases.
Having access to the alert log also allows operators to review past alerts which could make debugging future related alerts easier.

The map uses familiar interaction conventions (north-up orientation, clear mission boundary, and light grid partitioning) and communicates mission-state cues such as sea-state texture to reflect environmental state.
Combined with predictable swarm-path rendering from the coverage-planning model, these features were added to lower effort spent interpreting the User Interface and to reduce the mental overhead required to understand the locations of drones, anomalies, and their current states.

The visual language was also designed to reduce perceptual overload.
WCAG 2.2 AA contrast targets, aviation-style alert colours (critical red, warning amber, advisory blue, system green), and light/dark modes were added so high-priority information remains salient without saturating the display or sinking into other details.
In addition, simulation controls such as Fog-of-War and communication-degradation toggles were included so workload-relevant complexity could be deliberately introduced during mission runs.

\subsection{Evaluation Framework}\label{subsec:evaluation-framework}

BEACON uses a combination of operational metrics and self-reported workload scores with NASA-TLX to evaluate the effectiveness of the system in improving situational awareness and reducing operator workload.

Operational metrics include detection rate, time to first detection, search coverage, alerts per minute, comms uptime, and the amount of false positive or negatives.
These metrics were chosen to reflect both the system's performance in MSAR tasks and to measure the workload on the operator, as factors like excessive alerts can increase cognitive load, while factors like search coverage and detection rate reflect the system's effectiveness in achieving its core mission.
They were also easier to capture within the simulation, and similarly easier to analyse across different runs of the simulation, compared to more complex metrics like weighted situational awareness scores, which would be difficult to capture without real-world testing and human subject research.

Additionally, BEACON prompts users to fill in a NASA-TLX questionnaire at the end of each mission to capture the user's perceived workload during the mission.
NASA-TLX is a widely-used subjective workload assessment tool that measures perceived workload across six possible dimensions: Mental Demand, Physical Demand, Temporal Demand, Performance, Effort, and Frustration.
It was chosen in this context due to its widespread adoption in similar contexts, like aviation and human-factors cognitive load research (\cite{COLLIGAN2015469})\@.
The test is administered by prompting the user to rate each dimension on a scale from 0 to 100, then performing pairwise comparisons to determine which dimension is more important than the other, to calculate a weighted average workload score.
Typically, higher NASA-TLX scores indicate higher perceived workload.

At the end of a given mission, the user is presented with the Detection Rate, Duration of the mission, and the number of Alerts per minute, as well as a prompt to fill in the NASA-TLX questionnaire.

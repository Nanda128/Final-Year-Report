\section{System Architecture}\label{sec:system-architecture}

BEACON is implemented as a browser-based application for Maritime Search and Rescue swarm simulation.
The system follows a layered client-side architecture in which environment generation, swarm logic, communication effects, alerting, rendering, and evaluation are complete in-browser.
This arrangement avoids backend dependencies while preserving BEACON's deterministic scenario generation.

\subsection{Simulated Mission Area}\label{subsec:simulated-mission-area}

The simulated mission space is defined as a configurable maritime sector parameterized by width, length, seed, and anomaly configuration.
By default, the sector is 5km/5km, but users can adjust dimensions to explore different scales.

Environmental conditions are generated in a deterministic manner using a pseudorandom number generator.
This ensures that identical seeds yield the same sector geometry, sea conditions, and anomaly placements.

Each generated scenario contains environmental descriptors such as the sea's state, wind speed, and visibility, which can be used to inform drone battery consumption, sensor effectiveness, and speed.
They also include a set of anomalies, deterministically placed across the map, based on the seed.
The implemented anomaly classes are ``Person in Water'', ``Lifeboat'', ``Debris'', and ``False Positive''.
Anomaly placement is constrained to within the sector, and avoiding the Drone Hub in the center of the grid.

\subsection{Central Mission State and Simulation Engine}\label{subsec:central-mission-state-and-simulation-engine}

BEACON maintains mission state through a central application context that functions as an in-browser mission twin.
This state store holds the active scenario, the state of the drone fleet, sensor configuration, communication settings, Voronoi cells, coverage plans, detection logs, alerts and evaluation.
Mission execution gets divided into two principal update pipelines.

First, a frame-synchronized rendering loop updates the drone motion, heading, battery consumption, communication state, and path progress.
Second, a time sensor loop evaluates possible detections and false positives at a configured interval.

This separation allows continuous behavior while allowing behavior like sensing and event generation dependent on user-supplied parameters.

\subsection{Swarm Coordination, Coverage Planning, and Battery-Aware Autonomy}\label{subsec:swarm-coordination-coverage-planning-and-battery-aware-autonomy}

Swarm coordination combines spatial partitioning, coverage planning, and battery-aware autonomy to enable efficient search patterns.
In the context of BEACON, spatial partitioning is done through a weighted implementation of Voronoi Tessellation, derived from current drone positions and their individual speeds.
These cells are balanced such that faster vehicles cover proportionally larger cells so that the workload is distributed according to capability.

For each cell, a coverage plan is generated using a boustrophedon (lawnmower) search pattern, which is a common method for systematic area coverage (\cite{10.1007/978-1-4471-1273-0_32}).
This pattern is generated as a set of waypoints with a configurable overlap ratio, thereby providing a structured area search over random searching.
At runtime, these drones will follow these waypoints sequentially.

Energy management is implemented as a supervisory layer above path planning.
For each drone, the battery is estimated in minutes according to the type of drone and current environmental conditions.
It uses this battery life information, and the distance to the drone hub, to determine whether a drone has gone past a safe threshold to return to the Drone Hub.
When the projected battery life falls below the required margin, the battery management layer overrides any active movement tasks and redirects the vehicle to the Drone Hub in the center of the grid.
These battery warnings are then logged and propagated as alerts.

\subsection{Communications, Alerting, \& Debrief Data Pipeline}\label{subsec:communications-alerting-debrief-data-pipeline}

BEACON includes an optional communication model that represents signal degradation as a function of distance from the Drone Hub and configurable behavior.
From this model, the system simulates per-drone signal quality, latency, packet loss, and communication blackouts.

Event messages may then be transmitted immediately, delayed in a queue of outbound messages, or buffered while a drone is disconnected.
Through this mechanic, communication quality materially impacts the operator's situational awareness and ability to respond to events, as well as the drone's ability to report detections and receive commands.

Alert generation is implemented as a pure, rule-based system driven by mission events and drone states.
The system receives a stream of events, such as detections, battery warnings, and communication blackouts, into four tiers of alerting, inspired by Central Alerting Systems (EICAS) used in aviation (\cite{RN3}).
Alerts are categorized into four tiers, Advisory, Caution, Warning, and Status, based on their severity.
Each alert is also accompanied by a specific audio cue for each tier, to provide additional situational awareness through auditory channels.

When a mission ends, BEACON persists a snapshot of the mission metrics, before directing the user to an optional NASA-TLX questionnaire.
This debrief pipeline supports the subsequent visualization, export, and analysis of mission performance and subjective workload data.

\subsection{Presentation and Operator-facing Application Flow}\label{subsec:presentation-and-operator-facing-application-flow}

The user-facing side of the application is organized as a staged workflow comprising a ``main'' landing page, a setup page, an active simulation page, and a post-mission debrief sequence.
The landing page provides access to scenario presets, and saved custom scenarios, if any.
If they choose a preset, or create a new scenario, they are directed to the setup page, where they can adjust the scenario parameters, such as the number and type of drones and environmental conditions.
After launch, the user is directed to the simulation page, where they are presented with the mission map, a metrics dashboard, alert panel, environment status, and a detection log.
After the mission ends, they get directed to a debrief sequence, where they can perform a brief optional NASA-TLX questionnaire, and review their performance metrics.

Since simulation logic is separate from visual rendering, and stored in domain-operated modules, the architecture remains easily extensible.
In principle, the simulation could be extended to act as a true Digital Twin with a real-time data link to physical drones, while still preserving the current interface and analytics pipeline.
